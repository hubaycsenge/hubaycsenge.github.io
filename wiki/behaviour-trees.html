The execution layer of emotion-engine, and — following Csenge's decision of 2026-07-28 — the executive method for decisions made by reinforcement learning algorithms. py_trees and py_trees_ros are installed on robot-platform and already in use in mecanumbot-behaviours.

Primary source: colledanchise-ogren-behavior-trees.

How a BT works

A BT is a directed rooted tree in which internal nodes are control flow nodes and leaves are execution nodes. The root emits ticks at some frequency; a node runs only if ticked, and returns one of three statuses to its parent: Running, Success, Failure.

Node Symbol Semantics
Sequence → Tick children left to right; return Failure or Running as soon as a child does; Success only if all succeed
Fallback ? Tick children left to right; return Success or Running as soon as a child does; Failure only if all fail
Parallel ⇒ Tick all children; Success if M succeed, Failure if N−M+1 fail
Decorator — Custom transformation of a child's status (e.g. negation)
Action / Condition leaf Do something / test something

Fallback is also called selector or priority selector.

Why not an FSM — the argument that actually matters

The tradeoff between reactivity and modularity in FSMs is a one-way control transfer problem — the goto statement. To be reactive an FSM needs many transitions; many transitions are many one-way transfers, and as Dijkstra put it that is "too much an invitation to make a mess of one's program". Remove one component and every transition into it must be revised.

BTs use two-way control transfers governed by internal nodes. A leaf is written without knowing which node runs next — only what status to return. — colledanchise-ogren-behavior-trees §1.2, §2.6.1

Everything else follows from this: modularity, reusable subtrees, hierarchical organisation, readability, and suitability for automatic synthesis.

BTs generalise FSMs, hierarchical FSMs, the Subsumption architecture, Teleo-Reactive programs and Decision Trees (Ch. 2, formalised in Ch. 6). So choosing a BT does not forfeit anything those architectures could express.

The RL integration

This is why the source was ingested. colledanchise-ogren-behavior-trees Ch. 8 describes RL-BT: start from a hand-designed BT and replace selected nodes with Learning Nodes —

  • a Learning Action node wrapping Q-learning over a locally defined state, action set and reward; and
  • a Learning Control Flow node, a Fallback that learns the order to try its own children given the state.

The BT does not merely execute the policy — it decomposes the problem

"If RL-BT was started from scratch with a BT consisting of a single action, there would be no difference between RL-BT and standard RL. Instead, the point of combining BTs with RL is to address the curse of dimensionality, and do RL on smaller state spaces, while the BT connects these subproblems in a modular way." (§8.4)

Each learning node sees a small local state space; the tree supplies structure that would otherwise have to be learnt. Combined with sutton-barto-2018-rl §14.3 — the ethological repertoire as the admissible action set A(s) — this gives rl-for-behaviour-learning a two-source architectural argument.

The price, per the authors: RL-BT needs the designer to supply the tree structure and the states, actions and local reward for every learning node. That is more hand-authoring than plain RL, not less — which suits this thesis, because hand-authored structure is where the ethology lives.

The alternative in the same chapter, GP-BT, grows the tree itself from a single reward signal. Not recommended here: it would generate the behavioural structure that dog-human-interaction-model is supposed to supply.

Safety

Sequence(T_safe, T_learn) — a hand-authored safety subtree that overrides the learned tree. In GP-BT this is "the only part... that requires user input" (§8.2). Unsafe regions need a conservative margin so the safety action can act before it is too late.

This is a concrete answer to the problem sutton-barto-2018-rl §17.5 names and does not solve — safe embedding of RL agents in physical environments. For a robot learning around untrained humans it is load-bearing, and it should be in the thesis architecture from the start rather than retrofitted.

Watch for chattering: a naive safety sequence recharges to just over threshold, resumes, drops back, and oscillates (§3.4).

What the analysis chapters offer

  • Ch. 5 — state-space formalism for safety, robustness and efficiency, and for whether these are preserved under composition.
  • Ch. 9 — Stochastic BTs transformed into Discrete Time Markov Chains, giving Mean Time To Succeed, Mean Time To Fail and success probability over time, composable across subtrees.

Ch. 9 is directly relevant to Q3: "what makes real-time in a real environment defensible" has wanted an operational definition since the first ingest. MTTS and success probability computed over the actual tree are a defensible answer, and one that does not require running the robot to obtain. (Both chapters read for scope, not derived — re-read before claiming a formal guarantee.)

Design principles worth reusing (Ch. 3)

Explicit success conditions for readability; implicit sequences for reactivity — check the goal first, then preconditions, rather than checking outcomes; decision-tree structure for case handling; Sequence nodes for safety; backchaining to build deliberative trees; memory nodes when un-reactive behaviour is actually wanted; and choosing the right granularity.

Disadvantages, per the authors

  • The BT engine is complex to implement (ticking should run in parallel with action execution) — mitigated by using an off-the-shelf library, which robot-platform does.
  • Checking all conditions can be expensive. Relevant here: the platform now runs two neural detectors plus fusion, so condition evaluation is not free.
  • Feed-forward execution is fine in structured, predictable environments — BTs then add nothing.
  • BTs need a different mindset: "not focused on states but on conditions", and switching is tick driven, not event driven.
  • Tooling is less mature than for FSMs.

Relation to the rest of the architecture

Under rl-for-behaviour-learning the tree is the executor and decomposer, and a learnt policy the selector — which is option 3 of the three that this page previously listed as undecided, and it is also what mecanumbot-behaviours already does (trees publish Nav2 goals rather than driving wheels).

Against fuzzy-automaton-fri

The fuzzy automaton performs behaviour fusion — blending parallel component behaviours by necessity level — where a BT selects. Fuzzy fusion can express "somewhat anxious while still exploring"; a tick cannot, without explicit blending nodes. That remains a real loss.

But the automaton is a state machine, and §8.2.4.1 measured FSM node count growing exponentially under learning while the BT's growth rate declined. If the behaviour layer is to be learnt, that is a decisive argument. See Q9.

Emotion in a behaviour tree — the prior art

belle-2019-programming-with-affect (reference [9]/[10], held as of 2026-07-28) is the only work in the corpus joining emotion to behaviour trees. Its EMoBeT framework adds two node types:

  • Emotion Adder — fires an emotion, from a developer-supplied set of OCC emotions with hard-wired triggers. Single child.
  • E-Selector — selects an action from exactly two children by the sign of the character's current mood.

It answers this page's open question — by gating, and crudely

The item under To establish below asks whether emotional state gates the tree, re-weights it, or parameterises leaf actions. Belle et al. choose gating: an eight-octant PAD mood is collapsed to one bit at the moment of decision.

That is prior art to differ from, not to adopt. The wiki's existing argument stands and is now sharper: parameterising leaf actions fits dog-human-interaction-model, where approach appears under joy, fear, neutral and anger distinguished by manner rather than kind — and it fits robot-platform, whose expressive channels (LED colour, speed, proximity, neck angle) are continuous rather than a choice between two scripted lines.

Note also that EMoBeT's emotions are all triggered by scripted dialogue choices — hand-labelled events, exactly as in szabo-2011-emotional-engine. Neither the game-AI tradition nor the ethorobotics one closes the perception-to-emotion link. See thesis.

Still missing

The BT-and-emotion literature the two sources point at, none of it held: ALMA (Gebhard) — the layered affect model EMoBeT reimplements; the OCC emotion model (now held — ortony-2022-cognitive-structure, occ-model); GAMYGDALA, an OCC-based black-box appraisal engine for games; and Johansson & Dell'Acqua's earlier emotional selector node. See citation-backlog.

Still nothing on behaviour trees in social robotics or HRI: colledanchise-ogren-behavior-trees gives one paragraph (the JIBO SDK), and belle-2019-programming-with-affect is about game NPCs, not robots.
