What the clips establish

Compute and middleware. Ubuntu 22.04, ROS 2 Humble, CycloneDDS, ROS_DOMAIN_ID=19, colcon. Jetson Orin Nano at 192.168.1.240 on a dedicated MecanumNet; chrony time sync to the remote PC; systemd ros2.service autostart. Nodes detect the board at runtime by reading /proc/device-tree/model, so Jetson-only publishers are skipped on other machines.

Hardware. OpenCR microcontroller, LD08/LDS-02 lidar, an Arduino Nano driving the LEDs — all USB serial, addressed through udev rules (/dev/opencr, /dev/ld08_lidar, /dev/arduino_nano). INA219 current/voltage sensor on I²C. Wheel geometry: Ø65 mm, radius 32.5 mm, thickness 30 mm, separation x 129 mm, y 300 mm.

Internal-state telemetry — the Q2 blocker is gone. OpenCRState.msg is a full frame: goal and measured wheel velocities, positions, currents and accelerations, per-wheel error states, neck and grabber goal positions, DMS distance measure, battery voltage, and 9-axis IMU (angular velocity, linear acceleration, magnetometer, orientation quaternion). Separately, mecanumbot_sensorproc_node reads the INA219 and publishes orin_battery_state (Jetson only). Between them this is a richer internal-state stream than emotion-engine assumed.

Expressive output. Four addressable RGB LED panels (fl, fr, br, bl), each with mode + color, via the SetLedStatus / GetLedStatus services served by mecanumbot_led over serial to the Arduino Nano. Plus neck and grabber servos, plus holonomic motion.

Controller/teleop infrastructure, larger than expected: ButtonEvent, JoystickEvent, ControllerStatus, and a per-user database of named actions (ActionDescriptor / ActionTuple), controller mappings and recording schemes, all exposed as services. A recording scheme is a named list of topics to record per user — directly useful for validation-study data capture.

A simulation and evaluation harness. SimActor / SimActorArray describe simulated actors (id, name, kind, whether tracked subject, lidar visibility, pose, twist). SimBehaviorEvaluation and SimDetectionEvaluation are per-scenario automatic verdicts — unsafe-motion, proximity, wall-proximity, wrong-target and stale-detection flags; subject/actor/wall distances; false-wall and wrong-human lock flags; status and reason strings. Nothing in the corpus does automated behaviour scoring like this, and it bears directly on Q10.

Gaps in these sources

Still no commit SHAs

The clips remain undated snapshots of rendered README pages. No commit SHA is recorded for any repository, so nothing here can be pinned to a version. Two of the five clips (mecanumbot_msgs, mecanumbot_remote) record a licence — Apache-2.0; the other three record none.

For a thesis that will claim a working system, the SHAs matter. Ask Csenge to record git rev-parse HEAD for each repo, or clone them properly into raw/.

Also unrecorded:

  • LED mode and color enumerations — still used by value in examples (mode: 1, color: 3/4) and never defined here. mecanumbot_msgs says the tables are in the mecanumbot_led package README, which is not clipped.
  • Camera details — no resolution, frame rate, mounting position, or field of view for the CSI camera itself. The detector configs assume 640×480 or 1280×720 and a 60° horizontal FOV, but those are node parameters, not camera facts.
  • The audio stack — mecanumbot_audio is named in mecanumbot_msgs as a consumer of the audio types, but the package is not clipped and no microphone hardware is described. Whether audio is capture, playback, or both is undetermined, and it matters: capture enables vocal affect input, playback enables Morton's-rules vocalisation (dog-human-interaction-model).
  • mecanumbot_microcontrollers is no longer clipped at all. The previous clip was empty; now there is nothing. Low priority unless the LED or accessory firmware behaviour becomes relevant.
  • The README title still says "Raspberry PI" while its body documents the Jetson — an internal inconsistency in the upstream repo, not in this wiki.
