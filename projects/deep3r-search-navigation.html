Navigation strategies for Deep3R-based object search

Description

The robot has to find an object in a room it has seen before. In a first visit it explores the room while a GPU server builds a 3D reconstruction of it from the robot's camera stream (the Deep3R pipeline). Later, in a second visit, it is given a target — named in words — and has to find it, even if the object has been moved in the meantime.

This task is about how the robot moves during both visits: which exploration strategy produces a map good enough to search in, when to stop exploring, how to return to where the object was last seen, and how to search when it is not there any more. Several strategies are implemented, run side by side in simulation and on the robot, and compared.

Background — why we do it

Object search is a classic problem in active perception, and animals are very good at it. A dog that sees a toy hidden and then taken away first goes to where it last saw the toy, and then searches around that spot — searching intensively near the last evidence and widening out as time passes, a pattern ethology calls area-restricted search. Foraging theory adds a principled answer to when to give up on an area. Robotic search, by contrast, usually relies on frontier-based exploration or on full coverage, which treat every unexplored cell alike.

On the technological side, the robot's 2D LiDAR sees only one horizontal plane, while the server-side 3D reconstruction sees tabletops, chair legs and the target object itself. The navigation strategy decides which views the reconstruction gets, so it directly affects the quality of the map, and through it whether the object can be found at all. Localisation errors are also known to be mistaken for "the object has moved", so a good strategy relocalises before it concludes that something is missing. The project is part of my PhD work on a search behaviour modelled on the motivational (SEEKING) system of mammals.

Requirements for the finished system

  • At least three navigation strategies implemented as interchangeable behaviour-tree subtrees on top of Nav2 — for example a coverage/frontier baseline, go-to-last-seen-location, and area-restricted search spreading outward from the last-seen position.
  • An explicit stopping rule for the exploration phase and an explicit giving-up rule for the search phase, both configurable by parameter.
  • Integration with the existing server link: the strategies consume the server's map updates and found / not-found announcements, and switch between the exploration and search phases through the existing protocol.
  • A relocalisation check before the robot treats the target as absent from its remembered location.
  • A reproducible evaluation protocol in simulation (fixed rooms, object placements and random seeds) that logs, per run: time to find, path length, area covered, and whether the object was found or wrongly declared missing.
  • A comparison of the strategies over repeated simulated runs, followed by a smaller set of runs on the real robot in the lab.
  • Documentation: launch instructions, parameter reference, and a short report of the comparison.
